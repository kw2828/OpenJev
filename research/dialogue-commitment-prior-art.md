# Proposal and commitment memory: prior-art boundary

Primary-source review, 20 September 2026. This assesses the conditional [next-memory decision](dialogue-memory-next-decision.md); it is neither a protocol nor an admitted experiment. The active lexical-ablation scores were not read.

Four overlaps constrain the claim:

1. **Separate offered and accepted values already have a direct precedent.** TripPy keeps system-informed values apart from tracked dialogue state, then copies an informed value when the user accepts it. Its other copy sources are user spans and previously filled slots. Two registers plus a source-selection gate would largely reproduce this distinction. [TripPy, SIGDIAL 2020, sections 3.2–3.5](https://aclanthology.org/2020.sigdial-1.4.pdf)
2. **Retention and special-value decisions are established controls.** TripPy leaves state unchanged on its `none` operation and separately classifies Boolean and DONTCARE values. That operation must not be confused with OpenJev's NONE candidate, which denotes an actual unmentioned state. A comparator needs explicit carry versus clear semantics. [TripPy, sections 3.2 and 3.8](https://aclanthology.org/2020.sigdial-1.4.pdf)
3. **Deciding whether to write before selecting a value is SOM-DST's mechanism.** It predicts CARRYOVER, DELETE, DONTCARE or UPDATE, generating values only for UPDATE. Its training uses ground-truth previous states and operations; an autonomous OpenJev comparison must evaluate from its own predicted state and match supervision across arms. Renaming this decomposition proposal/commitment is not a new mechanism. [SOM-DST, ACL 2020, sections 3–4](https://aclanthology.org/2020.acl-main.53.pdf)
4. **Provenance and supersession also have explicit-state precedents.** StateMem records originating turn/speaker and dependencies, applies supersession, and marks dependent units for rechecking. This supports a strong structured-ledger control, not a claim that a provenance field is a new recurrent architecture. Its code/data release remains [unverified here](statemembench-release-review.md). [StateMem, arXiv v1, sections 5.1–5.2](https://arxiv.org/html/2608.19652v1#S5)

The strongest practical comparator is a schema-shared, finite-candidate operation ledger: committed candidate, pending proposal, source and age, with learned public-text evidence selecting carry, clear, DONTCARE or a concrete update. Proposal extraction must use the same visible text and paid observation computation as the proposed accumulator, not annotated system acts or gold previous state. Preserve TRUE/FALSE and every supplied candidate. Keep the ordinary scalar memory and an unrestricted two-register model with matched storage, inputs, supervision and objective; a GRU or reset-only control is insufficient by itself. These are local adaptations of established mechanisms, not claimed paper replications.

One testable distinction remains an **inductive-bias hypothesis**: separately controlling proposal writes and commitment writes might reduce premature commitment to SYSTEM offers while preserving correct delayed USER acceptance or correction after intervening turns. Test both revision and anti-update retention from model-generated state, beyond the shared short-history window. The unrestricted two-register control tests whether any gain is merely extra capacity; the explicit ledger tests whether ordinary operation prediction already suffices. Roles already appear in OpenJev inputs. No expressivity, novelty or efficacy claim follows from the register names. If the current observation ablation removes the relevant gap, or the explicit ledger matches the learned accumulator, this branch has no demonstrated architectural justification.
