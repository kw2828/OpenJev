# Jev screenshot claims: primary-source check, 25 September 2026

The public sources support direct decision readouts and shared-context computation. They do **not** establish Jev's private head dimensions, its exact RL algorithm, or a requirement to use RL for calibration. This updates the [earlier source check](decision-model-source-check.md) with pinned implementation details. Source inspection only: no weights downloaded, models executed, benchmarks rerun, or public writes made.

| Claim | Verified finding |
|---|---|
| Jev's architecture has been recovered. | [Archer Hume's article](https://archerhume.com/posts/jevs-architecture-unmasked/) reports black-box probes and explicitly distinguishes observations from proposed architecture. It leaves slot-based and pointer-style readouts unresolved. Backbone identity, sparse MoE and exact attention implementation remain conjectural. |
| Jev has an invariant 255-slot neural head. | [TypeSafe documents up to 255 options per Choice request](https://docs.typesafe.ai/primitives/choice). Hume says this limit is enforced by request validation and discusses a possible **256**-slot head as one hypothesis. An API cardinality limit does not determine a parameter matrix's dimensions. |
| SemLF is the former OpenJev. | The name is **SemIf**, capital I: [TheoLeeCJ/SemIf-OpenJev](https://github.com/TheoLeeCJ/SemIf-OpenJev/blob/23cf1f39fc9534fe81437200959b6dfc7106e45a/README.md). Its README says formerly OpenJev and disclaims TypeSafe affiliation. [zhihz/openjev](https://github.com/zhihz/openjev/tree/ff94f61ec3b2d6a71b4c2b01e76104dfe37da4e6) and this repository are separate projects. |
| Direct probabilities require removal of the LM head. | SemIf's [direct scorer](https://github.com/TheoLeeCJ/SemIf-OpenJev/blob/23cf1f39fc9534fe81437200959b6dfc7106e45a/src/semif_phase1/direct.py) reads the final-position vocabulary logits, selects answer-token rows and normalizes them. Its [loader and validator](https://github.com/TheoLeeCJ/SemIf-OpenJev/blob/23cf1f39fc9534fe81437200959b6dfc7106e45a/src/semif_phase1/core.py) retain a causal LM and accept 2-16 runtime options mapped to A-P. No generation loop is needed; the vocabulary projection remains. |
| Jevlike uses the same fixed head. | [Jevlike's model](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/model.py) makes each option a query, attends it to context and computes a shared dot-product score. The option dimension varies with the request and is masked for padding. `rank` is representation width, not the number of options. |
| RL is required for calibrated decisions. | [TypeSafe defines RLCD as Reinforcement Learning for Calibrated Decisions](https://docs.typesafe.ai/introduction/machine-learning-primer). Its [launch description](https://typesafe.ai/blog/introducing-system-one-models-and-jev) states the training objective, but the inspected public sources do not disclose the reward, loss, optimizer, data or complete training algorithm. That is a stated proprietary approach, not a necessity result. |

SemIf is a concrete counterexample to the last requirement: its [calibrator](https://github.com/TheoLeeCJ/SemIf-OpenJev/blob/23cf1f39fc9534fe81437200959b6dfc7106e45a/benchmarks/calibrate.py) fits one positive temperature by labeled NLL minimization, with bounds 0.05-20 and 60 golden-section iterations. Its evaluation uses group-disjoint folds. This is post-hoc supervised calibration, consistent with the established [temperature-scaling method](https://proceedings.mlr.press/v70/guo17a.html), not RL. Source inspection does not independently reproduce its reported empirical calibration gains. Positive temperature preserves argmax decisions; threshold-based abstention, coverage and downstream cost can still change.

Jevlike's [ordinary text trainer](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/train.py) uses supervised cross-entropy. Its [Doom example](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/examples/doom/README.md) also includes imitation, DAgger and experimental PPO. Therefore, “its scorer does not require RL” is supported; “the repository contains no RL” would be incorrect. None of these implementations establishes reproduction of TypeSafe's RLCD.

The [Qwen-2.5-1B-RLCD upload](https://huggingface.co/harshatheg/Qwen-2.5-1B-RLCD/tree/2af86848be75847ccb3553b0941cc51d6ef7e4e9) is especially easy to misread. At that revision the listed repository contains application/engine files, not a model-weight checkpoint. Its [Torch engine](https://huggingface.co/harshatheg/Qwen-2.5-1B-RLCD/blob/2af86848be75847ccb3553b0941cc51d6ef7e4e9/core/engine_torch.py) defaults to Qwen2.5-1.5B-Instruct, runs a prefix forward pass, copies/broadcasts its cache, then runs a suffix forward pass. It slices candidate logits and applies softmax. `has_calibrated_probabilities=True` is hardcoded; that flag supplies no calibration evidence. Likewise, its `sequential_forward_passes=1` field does not count both visible model calls. Its [255-option check](https://huggingface.co/harshatheg/Qwen-2.5-1B-RLCD/blob/2af86848be75847ccb3553b0941cc51d6ef7e4e9/core/schema.py) is schema validation, not a newly trained 255-row output head. These files do not implement an identified TypeSafe training recipe.

One additional distinction concerns confidence. The pinned [official adapter](https://github.com/typesafe-ai/system-one-adapter-python/blob/fb52b1030b7fc1f4f1cf39910afa5da54f9835e3/src/system_one_adapter/_utils/confidence_metrics.py) computes Choice confidence as `(max(p)-1/K)/(1-1/K)` after normalization, for K greater than one. With three options and maximum probability 0.8, that produces 0.7. This is a distribution-concentration transformation, not another learned correctness probability. Typed validity and normalization also cannot establish semantic correctness or calibration under a new workload or distribution shift.

## One missing baseline worth adding prospectively

For a future **text decision** comparison, add the same frozen language backbone with one final-position answer-token readout, with and without a separately fitted temperature. Hold prompts, candidate information and model precision fixed; validate token boundaries and score only the supplied labels. Compare it with a constrained **single-label-token** decode, charging complete tokenization, prefill, readout and cache-copy costs. Do not use a compulsory long JSON completion as the sole speed comparator: [jevlike's README](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/README.md) explicitly describes its quoted speed comparison as a decoder forced to write 400 tokens.

This tests whether a proposed recurrent mechanism adds quality or useful state reuse beyond an ordinary cheap readout. Evaluate held-out NLL/Brier, accuracy and decision cost separately, plus candidate permutations, missing-correct-option cases and irrelevant alternatives. Calibration fitting needs its own labels and split. SemIf's existing scorer is a reference implementation, not evidence of a new architecture.

There is also a precise limitation to retain in any later option-attention control: in the inspected jevlike text head each option's score is independent of the other options given context. With fixed temperature, adding another option cannot change the odds between two existing ones. That is a mathematical property of this code, not a property established for Jev. A candidate-set-dependent readout would be a different control. Neither finding validates a recurrent dynamical model or turns the current FSM regression experiment into a calibrated language decision system. No new experiment is authorized or launched by this note.
